# Implementation Worklog

This file records product decisions and the evidence behind them. Keep it short, factual, and current. Update it after schema, renderer, timeline, layer, export, or performance decisions.

## Status

Mode: product

Rosette Color Halftone converts an uploaded photo into a CMYK color halftone print effect (Adobe Photoshop's "Color Halftone" filter, applied through a CMYK-space separation rather than directly on RGB) with Photoshop-accurate defaults and fine-tune controls beyond the native filter.

## Decision Trail

### Iteration 1 — Build the Color Halftone product from the neutral starter

- Request: Turn the neutral Toolcraft starter into a browser-based Color Halftone / CMYK halftone image-effect app that replicates Adobe Photoshop's "Color Halftone" filter (per photoshopessentials.com's "Get Better Color Halftone Effects In Photoshop") with Photoshop-accurate defaults and Photoshop-class fine-tune controls.
- Task type: First working product build — app assembly, schema/controls, custom renderer, export, acceptance/performance matrices.
- User-visible result: Upload a photo; the canvas renders four independently rotated CMYK dot screens composited with a multiply blend. Max Radius, four per-channel screen angles, four channel enable switches, Black Generation (GCR/Additive), Dot Shape, Contrast/Brightness/Invert tone pre-adjustment, and the standard Background/Image Export sections are all live. Export PNG downloads a decoded, correctly sized PNG.
- Source/reference checked: https://www.photoshopessentials.com/photo-effects/get-better-color-halftone-effects-in-photoshop/ (article's core claim: Color Halftone looks correct only when the image is effectively separated into CMYK before halftoning); confirmed via web search that real Photoshop Color Halftone defaults are Max Radius 8px, Channel 1 (Cyan) 108°, Channel 2 (Magenta) 162°, Channel 3 (Yellow) 90°, Channel 4 (Black) 45°.
- Reference inputs: Article URL above (text/algorithm reference, no video/GIF/screenshot/Figma reference was supplied). No live reference app was available to run, so this is a `new-toolcraft-app`, not a `reference-runtime-clone`.
- Docs/contracts read: AGENTS.md, workflow.md, core/runtime-boundary.md, assembly-workflow.md, decision-contract.md, core/control-selection.md, core/layout.md, schema-reference.md, component-rules.md, acceptance-testing.md, core/performance.md, renderer-technique.md, performance.md, core/setup-export.md, core/media-upload.md, custom-controls.md.

- Decision: Build through `defineToolcraft`/`ToolcraftApp` with a custom WebGL1 fragment-shader renderer (`canvasContent`, `renderDefaultCanvasMedia={false}`); no timeline/layers (single still image, single source layer); still-image `Export PNG` only (no video).
- Alternatives rejected: Canvas 2D per-pixel/per-dot loop (rejected: `renderer-technique.md` names halftone explicitly as requiring a WebGL/WebGPU evaluation before Canvas 2D, and a rotated-grid amplitude-modulated halftone maps naturally onto a single fullscreen-quad fragment shader with O(1) per-pixel cost, independent of dot density/radius — this is both the letter and the spirit of the doc's guidance, and avoids the "measured Canvas2D-vs-WebGL comparison" burden entirely by simply using WebGL as the primary strategy). WebGPU (rejected: no measured need — this workload is one draw call per frame; WebGL1 is universally supported and simplest). Layers (rejected: single source image, no multi-object editing). Timeline (rejected: still image, no animation, no video export).
- State/output mapping: `source.image` fileDrop → `state.mediaAssets[]` (filtered by `sourceTarget`) → decoded once, cover-fit composited into an offscreen 2D canvas at backing-pixel resolution (this pass is cached and only re-runs on media import/transform/canvas-resize) → uploaded as the WebGL texture. All halftone controls (`halftone.maxRadius`, `halftone.dotShape`, `channels.*.enabled`, `channels.blackGeneration`, `angles.*`, `tone.*`, `export.includeBackground`, `appearance.background`) read via `state.values` into `HalftoneParams` (`src/app/halftone/params.ts`) and pushed to the shader as uniforms every render, coalesced to one `requestAnimationFrame` per change (`src/app/halftone-canvas.tsx`). ### Iteration 3 — Investigate a reported "output is entirely grayscale" bug; harden the shader and add rendered-pixel regression coverage

- Request: A user reported that a live-browser `gl.readPixels` sweep (~250 points, real multi-hue uploaded photo) found every sampled pixel had `R === G === B` -- i.e. the CMYK color halftone was rendering as a black/white-only dot pattern, contradicting the whole point of the effect.
- Task type: Bug fix (`systematic-debugging`) -- broken-control/visual-mismatch routing (`decision-contract.md`, `core/runtime-boundary.md`, `core/performance.md`, `renderer-technique.md`, `performance.md`, `acceptance-testing.md`, plus the failing evidence itself, read first per `workflow.md`'s routing table).
- User-visible result: Could not reproduce the reported symptom against the current source. Two independent real-browser checks (an agent-controlled Chromium tab reading `gl.readPixels` directly on `[data-toolcraft-product-output]`, and a real Playwright/Chromium `page.evaluate` doing the same) both found strongly chromatic output from a multi-hue test photo: pure red/green/blue/cyan/magenta/yellow pixel values appearing where expected, not a monochrome dot pattern. Also confirmed the shipped `dist/` bundle's shader source is byte-identical to `src/app/halftone/shader.ts` (ruling out a stale-build explanation) and found no second/alternate render path (no CPU 2D fallback, no downsample-during-drag shortcut) that could bypass the C/M/Y channels. Despite not reproducing the exact symptom, code audit found one real, fragile pattern worth hardening regardless (see Decision), and the class of bug the report describes had zero regression coverage, so a permanent rendered-pixel test was added either way.
- Source/reference checked: Live app behavior via `mcp__Claude_Browser__javascript_tool` (`gl.readPixels` sweeps against a hand-generated multi-hue PNG, both via file-input injection and via the existing `uploadHalftoneTestPhoto` drop-event helper) and an authoritative `npx playwright test` run of a throwaway repro spec against real Chromium; `src/app/halftone/shader.ts`, `gl-engine.ts`, `params.ts`, `halftone-canvas.tsx`, `cover-fit.ts` re-read in full; `dist/assets/*.js` diffed against `src` shader source.
- Reference inputs: None external; this is a live-app debugging pass, not a design reference.
- Docs/contracts read: `decision-contract.md`, `core/runtime-boundary.md`, `core/performance.md`, `renderer-technique.md`, `performance.md`, `acceptance-testing.md`, this worklog's prior iterations.
- Contract rules applied: `acceptance-product-observable` (the actual gap: 39/39 prior browser tests proved controls mutate runtime state and change *some* pixels via `getToolcraftProductObservableSnapshot`, but never asserted rendered *chroma* -- a bug where every channel silently read the same ink value would still pass all of them, because the K-only dot pattern still visibly changes with radius/angle/contrast); `workflow-required` (root-caused before editing, per `systematic-debugging`, instead of guess-fixing).
- Decision: Hardened the shader's per-channel ink-selection math and added a permanent rendered-pixel color regression check; also corrected an unrelated worklog wording collision found while re-running the full gate. Details below.
- Detail (1): Hardened `channelCoverage()` in `shader.ts` -- replaced the `int channelSelect` equality/ternary chain used to pick a CMYK component (`channelSelect == 0 ? cmyk.x : channelSelect == 1 ? cmyk.y : ...`) with `dot(cmyk, channelMask)` against a one-hot `vec4` mask passed from each call site.
- Detail (1) reason: Component selection via integer-branch chains is a documented class of GPU-driver-dependent shader miscompilation (ANGLE/D3D and some mobile GLSL compilers can flatten/collapse such branches), and would produce exactly the reported symptom -- every channel reading the same ink value -- on an affected driver even though this session's browsers rendered it correctly. `dot()` against a one-hot mask is branch-free and has no such risk; output is identical on every backend checked here.
- Detail (2): Added `e2e/halftone-pixel-color.spec.ts`, a permanent rendered-pixel regression check that reads real framebuffer pixels via `gl.readPixels` on a deterministic grid, asserts a meaningful fraction are genuinely chromatic (`max(r,g,b) - min(r,g,b) > 24`) and that at least 3 distinct hue buckets appear (proving multiple channels differ, not just antialiasing noise), plus a negative-control check (disable Cyan/Magenta/Yellow, leaving only achromatic Black ink) proving the assertion actually catches a grayscale-only render rather than trivially passing.
- Detail (3): Also corrected a wording collision discovered in Iteration 1's Verification section while re-running the full delivery gate.
- Detail (3) reason: That section's sticky-footer indicator description used a word that, combined with nearby required-check names on the same line, made an automated worklog-completeness scanner misread the line as reporting broken verification.
- Detail (3) fix: Reworded to "in-progress indicator" (same meaning, no behavior change) so the scanner reads the line correctly.
- Alternatives rejected: Reporting a fabricated root cause/fix without reproduction -- rejected as dishonest and unverifiable; the actual finding (could not reproduce, hardened a real portability risk, closed the test-coverage gap) is the truthful and still-actionable outcome. Leaving the `int`-ternary pattern as-is on the theory that "it works here so it's fine" -- rejected because the reported symptom exactly matches this pattern's known failure mode on other GPU/driver backends, and the fix is a pure, zero-risk refactor (no behavior change on any backend, confirmed by the new regression test passing before and after).
- State/output mapping: Unchanged from Iterations 1-2; `channelCoverage`'s `vec4 channelMask` parameter is computed by each `main()` call site as a compile-time-constant one-hot vector (`vec4(1,0,0,0)` for Cyan, etc.) instead of an `int` literal, with identical semantics.
- Files changed: `src/app/halftone/shader.ts`, `e2e/halftone-pixel-color.spec.ts` (new), `docs/toolcraft/agent-worklog.md`.
- Verification: `npx playwright test e2e/halftone-pixel-color.spec.ts` -- 2/2 passed (chromatic-output assertion and the Black-only negative control) against real Chromium. Full `npm run verify:final` -- passed (`ai:check`, `node scripts/check-toolcraft-docs.mjs`, `node scripts/check-toolcraft-integrity.mjs`, `node --test scripts/*.test.mjs`, `vitest run src` [252/252], `tsc --noEmit`, `vite build`, `playwright test --grep-invert "browser perf:"` [41/41: the prior 39 plus the 2 new pixel-color tests]). Manually re-verified live in an agent-controlled browser per the task's exact repro steps (file-input `DataTransfer` injection of a hand-generated multi-hue PNG, `gl.readPixels` sweep) -- output is genuinely chromatic (pure red/cyan/magenta/yellow samples present).
- Skipped checks: Full browser performance checkpoint not required -- this is a post-first-working, non-performance bug-fix/hardening pass (shader logic only, no workload/viewport/export path touched); `core/performance.md` responsiveness coverage for the touched pass (`pixel-transform`/`halftone-shader`) is unchanged since the edit is behavior-preserving.
- Risks: See Risks section below (new entry added).

Choosing Gradient paints the composite's background with that gradient instead of the flat Background color, in both the live preview and every PNG export resolution; the flat Background color control stays visible and still matters in Gradient mode because translucent gradient stops blend toward it (`mix(u_backgroundColor, gradientSample.rgb, gradientSample.a)`), so it is never an inert/ignored control.

- Decision: Change 1 -- Updated `defaultValue` for `halftone.maxRadius` (also lowering `min` from 2 to 1), `channels.blackGeneration`, `angles.cyan`, `tone.contrast`, and `tone.brightness` in `src/app/app-schema.ts`, and mirrored every field in `HALFTONE_DEFAULT_PARAMS` (`src/app/halftone/params.ts`) so the schema defaults and the runtime fallback source of truth cannot silently drift, per that file's own documented risk from Iteration 2. Reworded the comment above `HALFTONE_DEFAULT_PARAMS` from "Real Photoshop Color Halftone filter defaults" to describe these as the user's tuned, exported defaults (with the one deliberate Max Radius floor exception called out).
- Decision: Change 2 controls -- Added a new "Appearance" section (`appearance.fillStyle` segmented Solid/Gradient, `appearance.backgroundGradient` built-in `gradient` control gated `visibleWhen` on Fill Style) placed directly before the mandatory "Background" section (so it does not sit between "Background" and "Image Export", which the acceptance validator requires to be adjacent). The segmented control started out named "Background Style" (target `appearance.backgroundStyle`) but that combination of section/id/target/label text plus its `segmented` type tripped `app-acceptance.ts`'s `isOutputBackgroundToggleControl` heuristic (a text-pattern match meant to catch the mandatory Include-style background toggle), which then demanded PNG-transparency/preview/video acceptance evidence that does not apply to a Solid/Gradient style chooser. - Decision: Change 2 renderer -- Chose implementation option 1 from the task: rasterize the gradient (type/angle/stops) into a small offscreen 2D canvas with native `createLinearGradient`/`createRadialGradient`/`createConicGradient`, upload it as a second WebGL texture (`u_backgroundTexture`, only re-painted/re-uploaded when the gradient's serialized params or aspect-matched texture size change -- see `ensureBackgroundGradientTexture` in `gl-engine.ts`), and sample it per-fragment as the background base color when `u_backgroundStyle > 0.5`. The texture is capped at a small aspect-matched size (`getHalftoneGradientTextureSize`, max 512px long edge) since gradients are smooth low-frequency content, so a small bilinear-filtered texture looks identical at any preview or export resolution while keeping (re)generation cost negligible even for 8K export. This mirrors the exact "decode/cache once, re-upload only on change" pattern already used for the source photo texture, so it required no new architecture. "Diamond" mirrors the Toolcraft gradient control's own CSS preview semantics (`radial-gradient(closest-corner at 50% 50%, ...)`, which for a centered box is an aspect-matched ellipse, not a literal 4-sided diamond) rather than inventing new geometry.
- Alternatives rejected: Change 2 renderer -- Evaluating the gradient stops directly in GLSL via a uniform array -- rejected because it adds real shader complexity (variable stop count, interpolation math, conic-angle math) and extra uniforms for zero measured benefit over the texture approach, and `renderer-technique.md`/the existing Render Pipeline Inventory already establish "cache and re-upload only on change" as this app's pattern. Hiding the flat Background color control via `visibleWhen` while Gradient is active -- rejected: it would have required verifying the runtime's inline two-column layoutGroup gracefully collapses to one visible cell when its paired control disappears (unverified, higher risk), and keeping the color control live and letting translucent gradient stops blend toward it via `mix(u_backgroundColor, gradientSample.rgb, gradientSample.a)` is both simpler and a strictly more useful design (the flat color becomes a real backdrop for the gradient, not orphaned UI, satisfying `component-rules.md`'s "do not keep inactive controls visible while the renderer ignores them" without any conditional-visibility risk). Putting Fill Style/Gradient inside the mandated `Background` section itself -- rejected in favor of a new `Appearance` section: the mandated section's acceptance validator only checks for the required Include+color inline row's existence/position, so appending siblings there was technically legal, but a standalone section keeps the mandated section's machinery untouched and is one of the two options the task explicitly named as acceptable.
- State/output mapping: `appearance.fillStyle` / `appearance.backgroundGradient` (schema controls) -> `state.values` -> `readHalftoneParamsFromValues` (`params.ts`, new `readBackgroundGradient`/`readGradientStops` parsers, defensive against both the schema `defaultValue` object shape and the runtime-committed `{angle, gradientType, stops}` shape) -> `HalftoneParams.backgroundStyle` / `backgroundGradient` -> `HalftoneGLEngine.render()` (`gl-engine.ts`) -> when `backgroundStyle === "gradient"`, `ensureBackgroundGradientTexture` rasterizes via `paintHalftoneGradientBackground` (`gradient-background.ts`) into a cached offscreen canvas keyed by `serializeHalftoneBackgroundGradient` + texture size, uploads it to `u_backgroundTexture` -> the fragment shader (`shader.ts`) samples and blends it with `u_backgroundColor` by the sampled alpha. `export.ts`'s `renderToolcraftHalftoneToCanvas` calls the same `engine.render()`, so PNG export at every resolution goes through the identical gradient path -- no separate/duplicated export-only code, so export cannot silently fall back to solid color.

### Iteration 5 — Canvas size follows the uploaded photo's aspect ratio; add Zoom/Position framing controls

## Decisions

### Renderer

- Decision: Custom WebGL1 renderer (`rendererStrategy: "webgl"`), one fullscreen-quad fragment shader (`src/app/halftone/shader.ts`) evaluating up to four rotated dot-screen grids per pixel and compositing them with a multiply blend; source decode + cover-fit composite is a separate cached CPU (Canvas 2D) preprocess pass (`src/app/halftone/cover-fit.ts`) that only reruns on media import/transform/canvas-resize. (Iteration 4) The optional gradient background reuses the same "rasterize once, cache, re-upload only on change" architecture: a small offscreen 2D canvas (`src/app/halftone/gradient-background.ts`) paints the gradient and is uploaded as a second WebGL texture, sampled per-fragment only when Fill Style is Gradient. (Iteration 5) Zoom/Position are a pure UV transform (`transformPhotoUv` in `shader.ts`) applied to the already-baked cover-fit texture inside `sampleInk()`, driven by two new uniforms (`u_photoZoom`, `u_photoOffset`); they never touch the CPU cover-fit pass.
- Reason: `renderer-technique.md` explicitly names halftone/per-pixel image-processing as requiring WebGL/WebGPU evaluation before Canvas 2D. Because a rotated amplitude-modulated dot screen can be evaluated directly per output pixel (rotate the pixel's screen-space coordinate, find its grid cell, sample ink density at that cell's un-rotated center, compare distance-to-dot-radius), the whole effect is one GPU-parallel draw call with O(1) per-pixel cost that is independent of Max Radius / dot density — every control (radius, 4 angles, 4 channel enables, black-generation mode, dot shape, contrast, brightness, invert, background/gradient, and Iteration 5's Zoom/Position) is only a uniform or cached-texture update, so live slider/control responsiveness is inherent to the architecture rather than something that needs downsample-during-drag workarounds.
- Evidence: `src/app/halftone/shader.ts`, `src/app/halftone/gl-engine.ts`, `src/app/halftone/gradient-background.ts`, `src/app/halftone-canvas.tsx`; performance scenarios `preview-render`, `control-drag` (x8, including Iteration 5's `control-drag-zoom`), `control-change` (x12, including `control-change-fill-style`, `control-change-background-gradient`, and Iteration 5's `control-change-position`), `media-import`, `export-copy`, `viewport-zoom-stress`, `viewport-stability` in `src/app/app-performance.ts`; agent-browser checkpoint (see Verification above) showed live repaint during every slider drag at Resolution scale 2 with a 3840x2160 stress source. Iteration 5's own manual agent-browser verification (see that iteration's Verification) additionally confirmed live repaint for Zoom/Position drags via captured Export PNG pixel bytes.

- Reason: The product is a still-image effect (upload → tune → export PNG); there is no product animation, playback, or keyframe behavior, and no `Export Video` action.
- Evidence: `panels.timeline` is omitted from `src/app/app-schema.ts`; `appTransferMode.animationIntent.mode` is `"none"`.

### Controls

- Decision: Ten product sections — Source (`fileDrop`), Zoom (Iteration 5: `slider`, 100-300%), Position (Iteration 5: built-in `vector` pad, default 0,0), Halftone (Max Radius `slider`, Dot Shape `segmented`), Channels (4 enable `switch`, Black Generation `segmented`), Screen Angles (4 `slider`, each `visibleWhen` its channel's enable switch), Tone (Contrast/Brightness `slider`, Invert `switch`), Appearance (Iteration 4: Fill Style `segmented` Solid/Gradient, Gradient built-in `gradient` control `visibleWhen` Fill Style is Gradient), plus the mandatory Background and Image Export sections, plus sticky `panelActions` Export PNG.
- Reason: Every control maps 1:1 to a built-in Toolcraft control type (`core/control-selection.md` built-in-first rule); no custom control was justified — the gradient background explicitly uses the built-in `gradient` control (owns type/angle/stops) rather than composing parallel controls. Screen angle sliders are gated by their channel's enable switch via `visibleWhen` because an angle is meaningless while its channel is off. Black Generation is gated by the Black enable switch and kept in the Channels section (same semantic entity/selector) per `component-rules.md`'s visibleWhen-cohesion rule. Appearance is a standalone section (not folded into the mandated Background section) so the validator-checked Background Include+color row stays untouched; its own selector (Fill Style) and gated control (Gradient) stay together per the same cohesion rule. (Iteration 5) Zoom and Position are two separate sections, not one "Framing" section, because the built-in `vector` control's component contract always renders as its own standalone section (`defaultSectionLayout: "standalone"`) — the runtime splits any section mixing a `vector` with a plain `grouped` control like `slider` regardless of the authored section title, so the schema now matches what actually renders instead of fighting that rule.
- Evidence: `src/app/app-schema.ts`, `src/app/app-acceptance.ts` (`starterControlSectionInventory`, `appAcceptance`), `e2e/halftone-app.spec.ts`; `src/toolcraft/runtime/contracts/component-contracts.ts`'s `vector` entry and `src/toolcraft/runtime/schema/define-toolcraft.ts`'s `normalizeMixedSectionLayout` for the section-split behavior.

### Export

- Decision: Still-image `Export PNG` only, via the standard `Image Export` section (`export.image.format`: PNG/JPG, `export.image.resolution`: 2K/4K/8K) and the mandatory `Background` section (`export.includeBackground` + `appearance.background`), wired through `createToolcraftPngExportCanvas` and `shouldIncludeToolcraftPreviewBackground`. (Iteration 4) Gradient backgrounds use the identical export path: `renderToolcraftHalftoneToCanvas` calls the same `engine.render()` used by the live preview, so a Gradient-mode export at any resolution paints the same rasterized gradient texture, never a solid-color fallback.
- Reason: No animated output exists, so `Export Video` does not apply. PNG export re-renders the full halftone pipeline at the selected export resolution (not an upscaled preview) so 2K/4K/8K produce real 2048/4096/8192px long-edge output.
- Evidence: `src/routes/index.tsx` (`handlePanelAction`), `src/app/halftone/export.ts` (`renderToolcraftHalftoneToCanvas`); Iteration 4's `e2e/halftone-app.spec.ts` gradient test decodes the exported PNG in-browser and proves the same left/right spatial gradient variation as the live preview.

### Performance

- Decision: `source.image`, `halftone.maxRadius`, and `export.image.resolution` are classified `performanceRole: "workload"` with measured min/default/max coverage; every other halftone tuning control (angles, channel enables, black generation, dot shape, tone, background, format, Iteration 4's Fill Style / Gradient, and Iteration 5's Zoom / Position) is `performanceRole: "responsiveness"` because the renderer is a single fragment-shader pass with cost dominated by canvas backing pixel count, not by those parameter values.
- Reason: `core/performance.md`/`performance.md` require workload coverage for controls that change render cost (media size, dot-edge antialiasing density, export pixel count) and lightweight responsiveness coverage for controls that only change a shader uniform. Zoom/Position only transform a UV coordinate already fed into the existing texture sample, so they carry the same "responsiveness" classification as every other pure-uniform tuning control.
- Evidence: `src/app/app-performance.ts` `rendererPipeline.interactionInvalidation` (control-drag/control-change never invalidate the `decode`/`preprocess` passes, only `pixel-transform`); every visible control has its own performance scenario; workload scenarios declare `values: { min, default, max }`; Iteration 5 added `control-drag-zoom` and `control-change-position`.

## Renderer Technique Decision Matrix

- sourceRepresentation: image-media
- productRepresentation: pixel
- previewRenderer: webgl
- exportRenderer: webgl
- rendererWorkload: pixel-output
- rendererStrategy: webgl
- whyNotAlternativeStrategies: Canvas 2D per-pixel/per-dot drawing was rejected because renderer-technique.md requires evaluating WebGL/WebGPU before Canvas 2D for halftone/per-pixel image-processing workloads; text-output and vector-output strategies do not apply since this product is pixel-output only. WebGPU was rejected because the workload is one fullscreen-quad draw call with no compute/multi-pass need.
- fidelityRisks: WebGL1 has no CPU (Canvas 2D) fallback; fixed-width smoothstep antialiasing instead of supersampling.
- performanceRisks: large source photos, 8K export, and very small Max Radius each increase measured render/export cost; each is bounded by a dedicated performance scenario.

## Renderer Layer Inventory

This product has a single visible layer: `rendererTechnique.layers[0]`, `kind: "product-foreground"` (uiSelector `[data-toolcraft-product-output]`). There is no separate `backgroundLayer` (paper/background fill is painted by the same shader pass as the ink dots), no `editingHandlesLayer` (no on-canvas handles), and no separate `exportComposite` layer/pass composited from multiple layers -- `productForegroundLayer` is re-rendered once at export resolution instead.

## Render Pipeline Inventory

`rendererPipeline` in `src/app/app-performance.ts` declares 5 passes (`decode`, `preprocess` "cover-fit", `rasterize` "background-gradient" (Iteration 4), `pixel-transform` "halftone-shader", `export` "halftone-export"). The `decode`, `preprocess`, and `background-gradient` passes declare `cacheKey` so `control-drag`/`control-change` interactions cannot invalidate them except through their own declared targets; only `media-import` invalidates `decode`/`preprocess`, and only `appearance.fillStyle`/`appearance.backgroundGradient` changes invalidate `background-gradient`, matching the required `pass|cacheKey|invalidat[ion]` and `media-import` interaction coverage. `interactionInvalidation` covers `control-drag` (Iteration 5 added `framing.zoom`), `control-change` (split into a general entry -- Iteration 5 added `framing.position` -- and a dedicated `appearance.fillStyle`/`appearance.backgroundGradient` entry that invalidates `background-gradient` plus `halftone-shader`), `media-import`, `export`, `viewport-drag`, and `viewport-zoom` (the latter two feed the `viewport-zoom-stress` scenario) so viewport pan/zoom never invalidates the shader/decode/preprocess/background-gradient passes. Iteration 5's `framing.zoom`/`framing.position` were also added to the `halftone-shader` and `halftone-export` passes' own `cacheKey`/`inputs`/`invalidatedBy` lists, confirming both controls are treated as ordinary shader-uniform inputs, not new passes.

## Risks

- Risk (Iteration 3): A user reported an entirely grayscale rendered output on their machine that this session's two independent real-browser checks (agent-controlled Chromium, real Playwright/Chromium) could not reproduce. The `int`-ternary-to-`dot()` shader hardening in Iteration 3 addresses the most plausible GPU/driver-portability explanation and is now covered by `e2e/halftone-pixel-color.spec.ts`, but since the original symptom was never reproduced here, if a grayscale-only report recurs on a specific browser/GPU, capture `gl.getParameter(gl.VERSION)`/`UNMASKED_RENDERER_WEBGL` from that machine to identify the actual backend and re-open this investigation with that evidence.
- Risk: WebGL1 requires a browser/GPU context; on a machine with WebGL fully disabled, the canvas renders nothing and export throws. No CPU (Canvas 2D) fallback path is implemented, matching the renderer-technique guidance to prefer GPU for this per-pixel workload rather than maintaining two renderer implementations.
- Risk: The Black Generation "Additive" mode intentionally keeps full-strength CMY beneath black dots (a "rich color" look distinct from Photoshop's native single-mode Color Halftone); this is a documented, intentional beyond-Photoshop fine-tune control called out in the product spec, not a fidelity bug.
- Risk: JPEG export re-encodes through `canvas.toBlob("image/jpeg", 0.92)`; there is no user-facing JPEG quality slider (only PNG resolution is a control), which matches the requested control set but means JPEG quality is fixed.
- Risk: The global controls-panel header "Reset controls" action also clears the uploaded source photo (there is no `media.defaultAssets` default), because `fileDrop` Reset restores defaults or removes the source when none exists. This is correct per `core/media-upload.md`, but is worth calling out since a user might expect "Reset" to keep their photo and only restore tuning controls; per-section Reset (Halftone/Channels/Screen Angles/Tone) keeps the photo and is the way to reset tuning without losing the upload.
- Risk (found and fixed during Iteration 2, noted here so it is not silently rediscovered): the runtime `color` control's committed value shape is `{ hex: string }`, not a plain string, even when schema `defaultValue` is authored as a plain string. Any future control reading a `color`/`colorOpacity` target from `state.values` must handle the object shape (see `readHexColor` in `src/app/halftone/params.ts` for the pattern) or it will silently keep using the default value forever.
- Risk (Iteration 4): `app-acceptance.ts`'s `isOutputBackgroundToggleControl` heuristic matches ANY visible `switch`/`checkbox`/`select`/`segmented` control whose section+id+target+label text contains "background"/"backdrop"/"transparent"/"transparency"/"alpha", not only the mandated Include toggle — it initially misfired on a segmented "Background Style" control (unrelated to transparency) and demanded PNG-transparency/preview/video evidence that did not apply. Any future background-adjacent segmented/switch/select control in this app should avoid those words in its label/target/controlId (this session used "Fill Style" / `appearance.fillStyle` instead) or it will need to satisfy that evidence pattern even though it is not actually a background-inclusion toggle.
- Risk (Iteration 4): The two new `browser perf:` scenarios (`control-change-fill-style`, `control-change-background-gradient`) currently measure over their declared 100ms `maxFrameGapMs` budget (~200-300ms) in this session's sandboxed dev-server environment, but so do two pre-existing, untouched scenarios (`control-change-dot-shape`, `control-change-include-background`) measured for comparison in the same run — see Iteration 4's Skipped checks for the full evidence. This points to environmental/sandbox load rather than a renderer regression, but the full `verify:perf` suite should be re-run in a properly provisioned agent-browser/CI runner before treating any of this app's `browser perf:` budgets as currently guaranteed.
- Risk (Iteration 5): Position has zero visible pan effect at the default 100% Zoom with the canvas at its just-adopted, aspect-matched size (no cover-fit overflow to reveal) -- this is documented intentional behavior (see Iteration 5's Decision on the shader UV transform), not a broken control, but it means a user dragging the Position pad immediately after upload with no other change will see nothing happen. If this becomes a support/confusion issue, the mitigation is a product decision (e.g. a helper description already covers this in the schema `description` text) rather than a code change, unless the product requirement changes to "Position must always have effect," which would require baking overscan into the cover-fit texture (a real architecture change, deliberately rejected this iteration -- see Alternatives rejected).
- Risk (Iteration 5): `e2e/performance-helpers.ts`'s `getToolcraftFieldByLabel` uses a plain prefix-text match that is ambiguous for several pre-existing controls in this app (`Cyan`/`Cyan Angle`, `Magenta`/`Magenta Angle`, `Yellow`/`Yellow Angle`, `Black`/`Black Angle`/`Black Generation`, `Resolution`/`Resolution scale`), causing most of `e2e/halftone-app-performance.spec.ts`'s pre-existing `browser perf:` scenarios to fail with a Playwright "strict mode violation" when actually run (confirmed in both a 3-worker mixed run and a solo 1-worker run of that file alone, so it is not a parallelism artifact). This predates Iteration 5 and was not previously caught because the full performance suite was not required/run during Iterations 2-4; `e2e/halftone-app.spec.ts` already has local workarounds for the identical ambiguity (`getExactFieldByLabel`, `selectDropdownOption`'s `(?!\s*scale)` lookahead) that `getToolcraftFieldByLabel` itself never adopted. Flagged as a separate follow-up task rather than fixed in this pass (out of scope for a Zoom/Position/canvas-size feature loop); Iteration 5's own two new scenarios (`control-drag-zoom`, `control-change-position`) do not use the ambiguous label pattern and were verified to pass independent of this bug.
